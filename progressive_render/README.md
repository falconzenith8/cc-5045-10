# 设计评审渐进渲染服务（预览争用内核）

用户调整相机或材质时先得到**真实的低预算路径追踪预览**，配置稳定后再进入
**最终出图队列**。后台已有长任务时，交互请求仍获得**有限且可预测**的响应：
固定大小的渲染进程池 + 固定数量的累加器槽位 + 为紧急预览保留的交互通道，
资源不足时显式排队/返回限额，而不是无限启动进程制造表面快速。

全部基于 **Python 3 标准库**实现（`multiprocessing` + `http.server` +
手写 PNG/zlib 编码），无第三方依赖。

## 调度契约是配置，不是文档副本

释放配置 `config/scheduling_policy.json` 是调度的**唯一真源**。内核在启动时
从该文件读取所有数值；文件缺失或缺少必需键会**直接启动失败**，绝不回退到隐藏
默认值——旧配置因此不会被“看起来没事”的默认值掩盖。`engine/policy.py` 声明了
每个策略字段到内核常量的绑定，`tools/policy_validator.py` 逐一断言两边相等。

- 过期策略默认发布配置中不允许存在：`retired` 列表非空、`status` 不是
  `active`、或出现任何未知/已退役字段，校验器都会报错（不会因为“多了个键”而静默
  放过）。
- 文档声明同样被校验：预览/最终 spp、老化时间、紧急预览阈值、首帧 SLA、
  worker 预留公式、评审者限额、全局队列上限、槽位数量都必须与配置一致，
  文档写错数字会直接让 `policy_validator` 失败。

## 它真正交付了什么（不只是任务列表加优先级字段）

| 需求 | 实现位置 | 机制 |
|---|---|---|
| 可计量的计算片段 | `engine/kernel.py` | 每个作业切成 32×32 tile，每片固定 1spp（预览）/4spp（最终），分片是调度与预算的最小单位 |
| 优先级 + 等待时间调度 | `Kernel._score` | 分数 = 优先级 + 老化项；最终图基础分更高 |
| 防最终图饿死 | `Kernel._score` | 最终图等待超过 6 秒获得 +1000 跃升，连续预览无法永久阻塞它 |
| 紧急预览的交互通道 | `Kernel._pump` | 只要有紧急预览（p8 及以上）存活，就为它保留 1 个 worker，长最终任务最多占 workers-1；首帧 SLA 3000 ms |
| 抢占与恢复 | `_pump` + `render_chunk` + 时间线 | 调度抢占发生在**分片边界**（在途分片跑完再让位）；被取代/取消的预览在**行边界**停止，故取消后不可抢占的阶段至多一行。重新分派即续跑剩余分片，不重复也不漏采样；`preempted` 必有后续 `resumed` |
| 完整配置版本绑定 | `pathtracer.config_hash` | 每个作业冻结 scene+camera+材质+尺寸+spp，绑定 12 位 sha256 |
| 旧请求晚到不覆盖当前视图 | 内核取代 + 前端 stale-gate | 新相机/材质版本取代同评审者旧预览；前端按 `X-Cfg-Hash` 拒绝绘制过期帧 |
| 过时预览停止消耗预算 | `Kernel._cancel_locked` + worker 行级取消检查 | 取消事件置位，在途 tile 在下一行即停，槽位回收 |
| 资源不足明确排队/限额 | 槽位池 + 评审者限额 3 + 全局队列 24 | HTTP 429 带原因；槽位满则排队，不新建进程 |
| 失败反馈回预览争用 | `_worker` 捕获 + `_on_chunk` | 渲染异常变成作业 `failed` 并释放槽位，错误同时显示在预览与最终结果区 |
| 真实逐步改善的图像 | `snapshot_png` 每分片刷新 | 均值随有效采样数提升，颗粒感逐帧收敛，预览 4 spp 与最终 48 spp 质量严格区分 |

## 目录结构

```
progressive_render/
├── config/
│   └── scheduling_policy.json  # 调度契约（唯一真源，内核启动时强制读取）
├── engine/
│   ├── policy.py        # 策略加载 + 字段到内核常量的绑定（无默认值回退）
│   ├── pathtracer.py    # 真实蒙特卡洛路径追踪器 + PNG 编码 + 配置哈希
│   ├── scenes.py        # 三个复杂度递增场景 + 不可变配置构建
│   ├── kernel.py        # 预览争用内核：有界池/槽位/老化/保留通道/取代/时间线
│   ├── simulation.py    # 多位评审者演练（7 个场景，含预览争用样例）
│   └── server.py        # 标准库 HTTP 前端
├── web/
│   ├── index.html       # 出图任务面板 + 结果区 + 调度策略 + 时间线
│   └── app.js           # 内核驱动控件、版本 stale-gate、渐进轮询、优先级切换
├── tools/
│   ├── policy_validator.py   # 校验 config/内核/文档三者一致，拒绝过期策略
│   ├── maintenance_check.py  # 长任务+紧急预览：用排队时间/恢复状态核对实现
│   └── check_timeline.py     # 跑小任务并画时间线：标出资源上限与不可抢占阶段
├── run_server.py        # 启动 Web 服务
├── run_simulation.py    # 命令行演练并落盘 JSON/TXT 报告
└── reports/             # 演练报告输出目录（archive/ 下为过期样例）
```

## 怎样启动界面（预览争用的图形入口）

```bash
cd progressive_render
python3 run_server.py                 # 默认 127.0.0.1:8000
# 可选：python3 run_server.py --host 0.0.0.0 --port 8000 --workers 6
```

然后浏览器打开 **http://127.0.0.1:8000/**。这是预览争用的**主要入口**：

- 左上：选评审者、场景、相机（滑块拖动即连续发预览）、材质反照率、
  **预览优先级**（切到「8 · 紧急」即触发保留通道）；「提交预览」与
  「稳定配置 → 最终出图队列」两个按钮；可勾选关闭自动取代以演练限额。
- 中间：预览帧与最终渲染两个**真实运算**结果区（都是路径追踪输出，不是占位图），
  显示 cfg_hash、有效 spp、排队时间、首帧/完成延迟、恢复次数、进度条；
  过期帧有虚线警告且不会覆盖当前视图；渲染异常会以红色错误条出现在对应结果区。
- 右侧：内核实时 KPI、出图任务面板（状态/spp/分片进度/**排队**/**恢复**/停止按钮）、
  调度策略卡（来自 `config/scheduling_policy.json`）、执行时间线。

**切换预览优先级并提交后**，结果区立即按新版本重绘预览帧，任务面板与时间线会显示
新作业的调度；长最终任务仍在最终结果区继续推进直至完成。

命令行仅用于辅助预览争用的检查（见下）；日常交互请走上面的图形入口。

## 调度策略校验器与维护校验

```bash
python3 tools/policy_validator.py       # 配置 / 内核 / 文档一致，过期策略即失败
python3 tools/maintenance_check.py      # 长任务 + 紧急预览的排队时间与恢复核对
python3 tools/check_timeline.py         # 跑小任务并生成时间线（含资源上限标注）
```

- `policy_validator` 断言 33 个策略字段与内核常量逐一相等；未知/退役字段、
  非 active 的默认发布配置、与配置不一致的文档数字都会让命令以退出码 1 失败。
- 演练报告带有策略**指纹**（整个策略文档的 12 位 sha256）。只比对策略名不够：
  名字不变而数字被改过时，旧报告会被判为过期材料并拒绝，必须归档为 `STALE`
  后重新生成——这就是“陈旧材料需处置”的可执行版本。
- `maintenance_check` 在至少 4 个 worker 下跑一个 48 spp 最终任务同时打入紧急预览，
  从**执行时间线**重算每个预览的排队时间并与摘要值比对，并要求每个被抢占作业都
  出现 `resumed` 且最终进入终态；仅凭计数器不足以通过。
- `check_timeline` 跑一个 final + 被取代的预览版本，文本时间线显式标出资源上限
  （worker 池、槽位池、每作业在途、保留通道），以及调度抢占的分片边界与取消检查的
  行边界这两个不同的不可抢占阶段。
- `ui_flow_check.js` 在无浏览器环境下驱动真实 `web/app.js`：切换预览优先级、
  提交预览与最终出图、轮询真实 PNG 帧、注入失败，断言结果区确实出图且错误出现在
  面板上。它只是图形入口的自动辅助，不替代人工在 http://127.0.0.1:8000/ 的验收：

  ```bash
  python3 run_server.py --port 8033 --workers 4 &
  node tools/ui_flow_check.js
  ```

## 运行多评审者演练（记录延迟、排队时间、有效采样数、完成情况）

```bash
python3 run_simulation.py                 # 全部 7 个场景
python3 run_simulation.py --scenario preview_contention
```

场景：`camera_drag`（快速拖动版本取代）、`preview_flood`（预览洪泛下最终图不饿死）、
`quota`（评审者限额拒绝）、`failure`（失败反馈）、`long_final`（长任务中交互预览仍
有限响应并核对 SLA）、`priority`（切换优先级改变调度顺序）、`preview_contention`
（规范预览争用样例：长最终任务 + 紧急预览跑到底，用时间线核对排队时间与恢复）。
报告写入 `reports/rehearsal_<时间戳>.{json,txt}`，并带上策略指纹。也可在网页面板点
「运行多评审者演练」，走的是同一个真实内核。旧报告或策略数字已变时生成的报告
会被校验器判为过期材料——把它们移到 `reports/archive/*.STALE.*`，再按上面的
复现步骤重新生成当前证据。

## 关键边界与诚实的质量口径

- 预览固定目标 **4 spp**、最终 **48 spp**，UI 明确标注，低清预览不会冒充最终质量。
- 进程池大小 = `min(8, max(2, CPU - 2))`，累加器槽位 20 个，均在 worker fork 前
  预分配，这是硬资源上限；本环境 `/dev/shm` 仅 64MB，故刻意不依赖共享内存文件系统。
- 紧急预览的 3000 ms 首帧 SLA 要求至少 4 个 worker；更小的池会在 4 处如实报告
  SLA 无法满足，而不是假装达标。
- 抢占有两种粒度，且分工明确：**调度抢占**（更高优先级作业接手）在**分片边界**
  生效，在途分片会跑完；**取消**（被取代的预览）在**行边界**检查取消事件，所以
  取消后不可抢占的阶段至多一行像素。检查脚本把这两个边界都画在时间线头部。
- 渲染是真实路径追踪（漫反射余弦采样、金属反射、玻璃折射/Schlick、面积光、ACES 近似）。

## 预览争用样例在全新环境中的复现

```bash
cd progressive_render
python3 tools/policy_validator.py           # 1) 契约自洽
python3 tools/check_timeline.py             # 2) 小任务时间线可生成
python3 tools/maintenance_check.py --workers 4   # 3) 长任务 + 紧急预览通过
python3 run_simulation.py --scenario preview_contention   # 4) 规范样例跑到底
```

第 4 步要求 `completed_clean=true`：最终任务 done、每个预览的排队时间与时间线一致、
所有被抢占作业都已恢复并进入终态。这就是“预览争用在新环境依说明复现”的判据。
